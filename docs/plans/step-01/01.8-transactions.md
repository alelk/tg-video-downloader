## Stage decisions

- `dbQuery` удаляется. Репозитории выполняют запросы в текущей транзакции; без транзакции Exposed
  бросает — это ошибка программиста, её ловят тесты.
- **Вызовы вне use-case'ов** оборачиваются в `txRunner`: `JobProcessor` (каждая запись — короткая
  RW, каждое чтение — RO), `SystemSettingsHolder`, `VideoInfoCacheImpl`. Бот
  (`TelegramMiniAppAutoReplyBot`) в БД не ходит — проверить `grep`. Никогда не оборачивать yt-dlp,
  ffmpeg, HTTP.
- `VideoInfoCacheImpl.evictExpired` нигде не вызывается — не подключать (Not in), только перевести
  на текущую транзакцию.
- **`catchingDb`** (по `RepositorySupport.kt`): ловит только `SQLException`/`ExposedSQLException`,
  `CancellationException` пробрасывает. SQLSTATE `23505` → существующие конфликтные ошибки
  (`WorkspaceSlugConflict` и т.п.); остальное → новый `DomainError.DatabaseFailed` →
  `500 INTERNAL_ERROR` (добавить в исчерпывающий маппинг; wire тот же, что сейчас даёт `StatusPages`
  на `SQLException`).
- **Вложенный runner.** Тест: runner внутри runner переиспользует внешнюю транзакцию — откат внешней
  откатывает запись внутренней. Если Exposed 1.0 ведёт себя иначе — стоп, notes, статус `waiting`.
- **Репозитории** берут время из `Clock`; статусы и прочие enum в запросах — через существующий
  маппинг (`db/mapping/jobStatus.kt`), строковые литералы (`"pending"`, `"downloading"`) удаляются;
  значения в БД прежние (JSONB-фикстуры и round-trip из 01.4 это проверяют).
- **Use-case'ы** проверяются на ловушку «`Left` коммитится»: `either {}` внутри `inRwTransaction`
  возвращает `Left` без исключения, и уже сделанные записи коммитятся. Все проверки — до первой
  записи; где это невозможно — `Left` превращается в rollback способом из `transaction-runner.md`.
  Список проверенных use-case'ов — в notes.

## Work

2. `catchingDb`, `DomainError.DatabaseFailed`, маппинг ошибок.
