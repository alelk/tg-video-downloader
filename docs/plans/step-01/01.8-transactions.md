## Stage decisions

- `dbQuery` удаляется. Репозитории выполняют запросы в текущей транзакции; без транзакции Exposed
  бросает — это ошибка программиста, её ловят тесты.
- **Вызовы вне use-case'ов** оборачиваются в `txRunner`: `JobProcessor` (каждая запись — короткая
  RW, каждое чтение — RO), `SystemSettingsHolder`, `VideoInfoCacheImpl`. Бот
  (`TelegramMiniAppAutoReplyBot`) в БД не ходит — проверить `grep`. Никогда не оборачивать yt-dlp,
  ffmpeg, HTTP.
- `VideoInfoCacheImpl.evictExpired` нигде не вызывается — не подключать (Not in), только перевести
  на текущую транзакцию.
- **`catchingDb`** (по `RepositorySupport.kt`): ловит только `SQLException`/`ExposedSQLException`,
  `CancellationException` пробрасывает. SQLSTATE `23505` → существующие конфликтные ошибки
  (`WorkspaceSlugConflict` и т.п.); остальное → новый `DomainError.DatabaseFailed` →
  `500 INTERNAL_ERROR` (добавить в исчерпывающий маппинг; wire тот же, что сейчас даёт `StatusPages`
  на `SQLException`).
- **Вложенный runner.** Тест: runner внутри runner переиспользует внешнюю транзакцию — откат внешней
  откатывает запись внутренней. Если Exposed 1.0 ведёт себя иначе — стоп, notes, статус `waiting`.
- **Репозитории** берут время из `Clock`; статусы и прочие enum в запросах — через существующий
  маппинг (`db/mapping/jobStatus.kt`), строковые литералы (`"pending"`, `"downloading"`) удаляются;
  значения в БД прежние (JSONB-фикстуры и round-trip из 01.4 это проверяют).
- **Use-case'ы** проверяются на ловушку «`Left` коммитится»: `either {}` внутри `inRwTransaction`
  возвращает `Left` без исключения, и уже сделанные записи коммитятся. Все проверки — до первой
  записи; где это невозможно — `Left` превращается в rollback способом из `transaction-runner.md`.
  Список проверенных use-case'ов — в notes.

## Work

1. Тест вложенного runner'а (сначала — чтобы знать поведение).
2. `catchingDb`, `DomainError.DatabaseFailed`, маппинг ошибок.
3. Репозитории: убрать `dbQuery`, `Clock`, enum-маппинг вместо литералов.
4. Обернуть вызовы вне use-case'ов.
5. Ревью use-case'ов на «`Left` коммитится».
6. Smoke-тест `JobProcessor` с фейковым загрузчиком.
7. `docs/DATABASE.md`, `docs/ARCHITECTURE.md` — раздел о транзакциях.

Отклонения / решения исполнителя:
1. **`catchingDb` — только там, где порт возвращает `Either`.** Finder'ы, `delete`, `removeMember`,
   `saveAll`, методы кэша возвращают значения, а не `Either`; менять сигнатуры портов план не предусматривает.
   Их `SQLException` идёт исключением → runner откатывает → `StatusPages` → тот же `500 INTERNAL_ERROR`.
2. **Конструкторы репозиториев и `SystemSettingsHolder` изменились** → в тестах 01.4 (`*RepositoryImplTest`,
   `JsonbFixturesTest`, `SystemSettingsHolderTest`) поменялись только аргументы конструкторов (и в двух
   местах снята лишняя обёртка `tx.inRwTransaction { SystemSettingsHolder(…) }`, чтобы уложиться в 120
   колонок — загрузка теперь сама открывает транзакцию); ожидания не менялись. Комментарии о «DB default»
   в трёх тестах исправлены на фактические.
3. **Время insert'а — из доменного объекта**, а не из `DEFAULT now()` (находка 01.4). Остаток: ответ на
   create несёт наносекунды `Clock`, в БД — микросекунды (`timestamptz`); расхождение < 1 мкс вместо ~1 мс.
   Усечение `Clock` до микросекунд — не в объёме стадии.
4. **Конфликты по индексам:** кроме `WorkspaceSlugConflict`, `23505` на `idx_jobs_active_video` отображается в
   существующий `JobAlreadyExists` (раньше гонка двух `POST …/jobs` давала 500, теперь 409 — как у проверки
   в use-case'е). Дубль участника / канала (`23505` без доменного конфликта) — `DatabaseFailed` → 500, как раньше.
5. **Исключение из «только runner открывает транзакцию»:** `DatabaseReadinessProbe` (`SELECT 1` через
   `transaction(db)`) — так разрешает `exposed-postgres` для health-проб; зафиксировано в `DATABASE.md` §7.1.
6. **`JobProcessor`:** `@Suppress("LongParameterList")` с причиной (10 параметров; разбиение — Not in);
   ветка `CancellationException` → `CANCELLED` теперь идёт через `writeStatus`, но в отменённой корутине
   `withContext` runner'а сразу бросает — запись не происходит, **как и раньше с `dbQuery`**; ветку удаляет 01.9.
7. Static analysis: `JobProcessor.kt` отформатирован (wildcard `kotlinx.coroutines.*` → явные импорты, длинные
   строки разбиты). ktlint baseline: infra 423 → 281, transport 42 → 37 (у `respondEither.kt` осталась только
   `filename`); Detekt: infra 65 → 41, transport 17 → 14; три ID `JobProcessor` (`LongMethod
   processAdditionalOutput`, два `TooGenericExceptionThrown`) заменены теми же находками с новой сигнатурой после
   форматирования (число не выросло). Новые файлы — без записей.
