## Stage decisions

- **Таблица переходов в domain** (`JobStatus`):
  - `PENDING` → {`DOWNLOADING`, `CANCELLED`};
  - `DOWNLOADING` → {`DOWNLOADING`, `POST_PROCESSING`, `COMPLETED`, `FAILED`, `CANCELLED`, `PENDING`};
  - `POST_PROCESSING` → {`POST_PROCESSING`, `COMPLETED`, `FAILED`, `CANCELLED`, `PENDING`};
  - `FAILED` → {`PENDING`}; `CANCELLED` → {`PENDING`}; `COMPLETED` → {}.
  - `isCancellable`/`isRetryable` выводятся из таблицы и обязаны совпасть с текущими (тест по всем статусам).
- **Методы `JobRepository`.**
  - `transition(id, expected: Set<JobStatus>, to, patch)` — один `UPDATE … WHERE id = ? AND status IN (…)`.
    0 строк → `Left(DomainError.JobStatusConflict(id, actual))`. Retry увеличивает
    `attempt = attempt + 1` в SQL.
  - `claimNext()` — атомарный `PENDING → DOWNLOADING` (`FOR UPDATE SKIP LOCKED`, `ORDER BY created_at`),
    выставляет `started_at`.
  - `requeueInterrupted()` при старте: `DOWNLOADING`/`POST_PROCESSING` → `PENDING`, прогресс
    обнуляется, `attempt` не меняется (Fork 2).
  - `updateStatus` (безусловная запись) удаляется.
- **Wire.** `CancelJobUseCase`/`RetryJobUseCase` переводят `JobStatusConflict` в существующие
  `JobCannotBeCancelled`/`JobCannotBeRetried` с фактическим статусом — HTTP-ответ тот же, что сейчас.
  `JobStatusConflict` в исчерпывающем маппинге получает те же статус и `code`, что
  `JobCannotBeCancelled` (новых кодов не вводим).
- **Поллер.**
  - Пока есть свободный слот: `claimNext()` одной задачи и запуск её корутины.
  - Каждый тик — проверить статусы запущенных id; задача больше не активна (отменена через роут) →
    отменить корутину этой задачи.
- **Записи прогресса и итога** — CAS из активных статусов. `Left` → отменить корутину задачи и
  больше ничего не писать.
- **Процессы.**
  - Ожидание в `YtDlpRunner`/`FfmpegRunner` отменяемое (не блокирующий `waitFor()` в корутине).
  - При отмене: `descendants().destroy()`, затем `destroy()`, ждать ≤ 5 с, затем `destroyForcibly()`.
  - Циклы чтения stdout завершаются.
- **Остановка.**
  - `suspend fun stop(grace: Duration = 10.seconds)`: перестать захватывать; отменить работающие
    задачи с причиной `ShutdownCancellation`; вернуть их в `PENDING` в `NonCancellable` (CAS из
    активных статусов).
  - Хук `ApplicationStopping` вызывает `stop` через `runBlocking` + `withTimeout`.
  - Ветка, ставящая `CANCELLED` на `CancellationException` в `processJob`, удаляется: `CANCELLED`
    ставит только `CancelJobUseCase`.
- **Конфиг и развёртывание.** `maxAttempts`/`retryDelayMs` не трогать. Один инстанс сервера —
  задокументировать. Индекс для `claimNext`, если нужен, — только новой миграцией `V9`
  (+ запись в `DATABASE.md`); `V1…V8` не трогать.

Отклонения / решения исполнителя:
1. `claimNext(): Job?` и `requeueInterrupted(): Int` без `Either`/`catchingDb` (как прочие не-`Either` методы
   порта, 01.8 отклонение 1): исключение уходит в поллер (лог, повтор на следующем тике; восстановление на

   успеет — задачи остаются `downloading` и возвращаются в очередь при следующем старте (проверено тестом 3).
