# Stage 02.1 — Reproduce and identify tested artifacts

> Execution amendment (owner, 2026-10-31): implement the first candidate now; the owner will
> check the affected iPhone after deployment. This supersedes device-first prerequisites
> below. No physical-device measurements are claimed; see the overview for approved scope.

## Read before starting

Read the [index](README.md), [overview](../step-02-ios-keyboard.md),
[research](../../research/ios-telegram-keyboard.md) and `CLAUDE.md`.

## Stage decisions

K2, K3 and K7 apply. No production behavior changes in this stage. Device evidence is required
before the repair; do not invent a test that checks only HTML text or library version.

## Work

1. Record phone/iOS/Telegram versions, launch path, external keyboard state and deployed image.
   Check ordinary typing is possible in Telegram itself.
2. Record served HTML/JS hashes and cache headers through the actual ingress. Reopen the Mini App
   to verify the tested artifact is loaded. Treat current nginx `no-cache` as revalidation policy.
3. Obtain the actual JS runtime dependency graph, including composite substitution. Record whether
   the sibling wrapper or published fork was used; identify its sources. A fresh local build must
   not be confused with existing generated files.
4. In an isolated local diagnostic fixture opened through Telegram, compare a visible normal
   HTML input, minimal Compose field and application field. Include the unmodified app baseline
   and a variant with only the global bridge removed. Give the native control its own labeled
   area; it must receive the actual tap, not sit behind or invisibly over the canvas.
5. Capture a failing run: event/focus timing, own-root active element, geometry and user-visible
   keyboard state. Follow the research's data restrictions. Record Safari as a control separately.
6. Save the reproduction procedure and anonymized observations in executor notes. If the native
   input also fails, investigate host/device/overlay issues before attributing the defect to Compose.

## Checks and done when

The failing device behavior is recorded against known assets, and the native-control comparison
separates host-level failure from Compose behavior. Dependency provenance is known. If a fixture
is added, run `./gradlew build`; keep device steps as an explicit supplemental check. Advance
only when evidence supports 02.2, or record the mismatch and revise the plan before fixing it.
